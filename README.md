# Расписание ресторана — restaurant-schedule-app

Простое мобильное PWA-приложение для управления недельным расписанием
официантов и посудомойщиков: сотрудники сами указывают, когда могут
работать, администратор задаёт потребность по ролям и интервалам времени,
система автоматически считает покрытие, находит нехватку и рассылает
push-уведомления, чтобы быстро найти человека на смену.

Первая версия работает с **одной конкретной неделей** (архитектура
позволяет позже легко добавить автоматическое создание следующих недель —
см. раздел [«Что легко расширить»](#что-легко-расширить)).

## Статус этапов разработки

- [x] Этап 1: проект, БД, пользователи, админ, языки, базовый интерфейс
- [x] Этап 2: расписание, временные интервалы, потребности, расчёт покрытия
- [x] Этап 3: дефицит, запросы сотрудникам, приоритет посудомойщика
- [x] Этап 4: push-уведомления
- [x] Этап 5: приход/уход, история, ручное редактирование админом
- [x] Этап 6: PWA, мобильная оптимизация, тесты, деплой

## Стек и почему именно он

Главная цель — бесплатный, максимально простой для новичка стек, который
при этом даёт **настоящую** серверную логику и push-уведомления (просто
статического сайта на GitHub Pages для этого недостаточно — нужна база
данных, проверка прав доступа на сервере и способ отправлять push).

| Часть | Технология | Почему |
|---|---|---|
| Фронтенд | **React + TypeScript + Vite** | Самый распространённый стек, много обучающих материалов, Vite — быстрая и простая сборка |
| Стили | **Tailwind CSS v4** | Позволяет быстро делать аккуратный mobile-first интерфейс без написания отдельных CSS-файлов |
| Роутинг | **React Router** | Стандарт де-факто для многостраничных React-приложений |
| Локализация | **react-i18next** | Готовое решение для 3 языков, поддерживает склонения (важно для русского: 1 человек / 2 человека / 5 человек) |
| PWA | **vite-plugin-pwa + Workbox** | Генерирует manifest и service worker автоматически |
| База данных + сервер | **Supabase** (бесплатный тариф) | PostgreSQL «из коробки», авторизация, Row Level Security (проверка прав **на сервере**, а не только в интерфейсе), Realtime, Edge Functions — всё в одном бесплатном сервисе, **без банковской карты** |
| Push-уведомления | **Web Push (VAPID)** через Supabase Edge Function | Стандартный браузерный Push API, не привязан к конкретной корпорации |
| Хостинг фронтенда | **GitHub Pages** через GitHub Actions | Бесплатно, ровно то, что просили |

### Почему Supabase, а не Firebase

Оба варианта разумны, но у Supabase два важных преимущества для этого
проекта:

1. **PostgreSQL — реляционная база.** Техзадание явно требует «не хранить
   всё в одной огромной таблице» и нормальную структуру с отдельными
   сущностями — это ровно то, для чего создан PostgreSQL, а не
   NoSQL-хранилище вроде Firestore.
2. **Не нужна банковская карта.** Функции Supabase (Edge Functions)
   работают на бесплатном тарифе без привязки карты. У Firebase
   аналогичные серверные функции требуют платный тариф Blaze (даже если
   по факту ничего не будет списано).

### Почему не только GitHub Pages

GitHub Pages отдаёт только статические файлы — он не может сам считать
покрытие, проверять права доступа или отправлять push. Поэтому фронтенд
(статические файлы) живёт на GitHub Pages, а вся логика и данные — в
Supabase. Браузер сотрудника обращается напрямую к Supabase по HTTPS.

## Структура базы данных

Каждая сущность — отдельная таблица (не «одна большая таблица»):

| Таблица | Назначение |
|---|---|
| `schedule_weeks` | Единственная активная неделя (даты, часовой пояс) |
| `employees` | Сотрудники: имя, телефон, привязка к анонимной сессии входа |
| `employee_roles` | Роли сотрудника (официант/посудомойщик), м:м |
| `admin_profiles` | Кто из пользователей Supabase Auth — администратор |
| `staffing_requirements` | Потребность: день + роль + интервал + сколько человек |
| `shifts` | Фактически заявленные/назначенные смены |
| `shortage_records` | Обнаруженные нехватки (с памятью о «пропущено») |
| `shortage_requests` | Запросы сотрудникам с очередью приоритета |
| `shortage_responses` | Ответы «выйду / не могу» на запросы |
| `attendance` | Фактический приход/уход (план vs факт) |
| `schedule_conflicts` | Обнаруженные пересечения смен одного сотрудника |
| `push_subscriptions` | Подписки браузеров на push |
| `notifications` | Лента уведомлений (тип + данные, локализуется при показе) |
| `audit_log` | Полная история изменений (append-only) |

Права доступа проверяются **в базе данных** через Row Level Security
(RLS) — это значит, что даже если в интерфейсе будет ошибка, сотрудник
физически не сможет получить чужой телефон или изменить чужую смену:
запрос будет отклонён самим PostgreSQL. Список сотрудников без телефонов
отдаётся через отдельное view `employee_roster`, в котором просто нет
столбца с телефоном — утечка структурно невозможна.

Подробности — в комментариях внутри файлов `supabase/migrations/*.sql`,
они написаны так, чтобы объяснять «почему», а не только «что».

## Быстрый старт: локальный запуск

### Что понадобится

- [Node.js](https://nodejs.org/) версии 22 (см. файл `.nvmrc`)
- Аккаунт на [supabase.com](https://supabase.com) (бесплатно, без карты)
- Git

### 1. Скачайте проект и установите зависимости

```bash
git clone <URL вашего репозитория>
cd g
npm install
```

### 2. Создайте проект Supabase

1. Зайдите на [supabase.com](https://supabase.com) → **New project**.
2. Придумайте пароль базы данных (сохраните его — пригодится редко, но
   пригодится) и выберите регион поближе к ресторану.
3. Дождитесь создания проекта (1–2 минуты).
4. Слева в меню откройте **Project Settings → Data API** — скопируйте
   **Project URL**.
5. Там же откройте **API Keys** — скопируйте ключ **anon public**.

### 3. Включите анонимный вход (обязательно!)

Сотрудники регистрируются без пароля — под капотом это «анонимный» вход
Supabase Auth, привязанный к телефону. По умолчанию эта функция
**выключена**, её нужно включить один раз:

**Authentication → Sign In / Providers → Anonymous Sign-Ins → Enable.**

Если этого не сделать, экран регистрации покажет понятную ошибку с
просьбой обратиться к администратору — но лучше включить сразу.

### 4. Примените схему базы данных

Самый простой способ — через веб-интерфейс, без установки чего-либо:

1. В Supabase откройте **SQL Editor**.
2. Откройте по очереди файлы `supabase/migrations/0001_...sql`,
   `0002_...sql` и так далее **строго по номерам**, копируйте содержимое
   и нажимайте **Run**.

Либо через [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started):

```bash
npx supabase login
npx supabase link --project-ref <ваш project ref из URL проекта>
npx supabase db push
```

### 5. Настройте дату недели

Миграция `0007` создаёт одну неделю по умолчанию (21–27 сентября 2026,
часовой пояс Europe/Moscow). Откройте **Table Editor → schedule_weeks** и
поправьте `start_date`, `end_date` и `timezone` на реальные для вашего
ресторана (например, `America/Sao_Paulo` для Бразилии).

### 6. Заполните переменные окружения

```bash
cp .env.example .env.local
```

Впишите в `.env.local` значения из шага 2 (`VITE_SUPABASE_URL`,
`VITE_SUPABASE_ANON_KEY`). `VITE_VAPID_PUBLIC_KEY` можно пока оставить
пустым — заполните на шаге про push-уведомления.

### 7. Запустите

```bash
npm run dev
```

Откройте адрес из терминала (обычно `http://localhost:5173`) на
телефоне или в мобильном режиме браузера (DevTools → Toggle device
toolbar).

## Создание аккаунта администратора

Регистрация администратора **намеренно не сделана через сайт** — это не
дыра, а осознанное решение: иначе кто угодно смог бы сам назначить себя
администратором. Первого администратора создаёт тот, у кого есть доступ
к Supabase-проекту:

1. В Supabase: **Authentication → Users → Add user → Create new user.**
   Укажите email и пароль. Email можно не подтверждать (Auto Confirm
   User — включите галочку).
2. Скопируйте **User UID** созданного пользователя.
3. Откройте **SQL Editor** и выполните (подставив свой UID):

```sql
insert into admin_profiles (user_id, display_name)
values ('ВСТАВЬТЕ-UID-СЮДА', 'Имя администратора');
```

4. Откройте сайт → `/admin` → войдите под указанными email/паролем.

Дополнительных администраторов создавайте так же.

## Push-уведомления: настройка

Это единственная часть, требующая ручной настройки внешнего инструмента
(бесплатного). Без неё сайт продолжит работать — просто не будет
приходить push, когда приложение закрыто.

### 1. Сгенерируйте VAPID-ключи

VAPID-ключи — это как «удостоверение личности» вашего сайта перед
push-сервисами браузеров. Один раз сгенерируйте пару и сохраните:

```bash
npx web-push generate-vapid-keys
```

Вы получите `Public Key` и `Private Key`.

### 2. Добавьте ключи в Supabase (Edge Function secrets)

**Project Settings → Edge Functions → Secrets** (или через CLI):

```bash
npx supabase secrets set VAPID_PUBLIC_KEY=<публичный ключ>
npx supabase secrets set VAPID_PRIVATE_KEY=<приватный ключ>
npx supabase secrets set VAPID_SUBJECT=mailto:ваш-email@example.com
```

### 3. Опубликуйте Edge Function

```bash
npx supabase functions deploy send-push --project-ref <ваш project ref>
```

### 4. Подключите автоматический вызов при новом уведомлении

Проще всего через интерфейс (не требует правки SQL):
**Database → Webhooks → Create a new hook**:
- Table: `notifications`, событие: `INSERT`
- Type: `Supabase Edge Functions`, function: `send-push`

(Альтернатива — выполнить `supabase/migrations/0018_notification_webhook.sql`
вручную в SQL Editor, заменив `YOUR_PROJECT_REF` на свой — делает то же
самое, но через SQL.)

### 5. Добавьте публичный ключ во фронтенд

В `.env.local` (и позже — в секреты GitHub Actions, см. деплой):

```
VITE_VAPID_PUBLIC_KEY=<тот самый публичный ключ>
```

### Как проверить, что push реально работает

1. Откройте сайт на телефоне (после деплоя — по HTTPS, локально по
   `localhost` тоже работает).
2. Как сотрудник или администратор — разрешите уведомления, когда
   появится баннер на главном экране.
3. Полностью закройте вкладку/приложение.
4. Вызовите любое действие, создающее уведомление (например, попросите
   другого сотрудника изменить смену) — должно прийти системное
   push-уведомление.

> В этой среде разработки (изолированный контейнер) у меня не получилось
> протестировать самую последнюю милю — реальную доставку через push-сервис
> браузера (сетевые ограничения песочницы). Вся остальная цепочка проверена
> напрямую: локализация текста уведомлений — тестами (`deno test`,
> `supabase/functions/send-push/messages.test.ts`), подписка и таблица
> `push_subscriptions` — через RLS-тесты. Проверьте живую доставку один раз
> после деплоя по шагам выше.

## Бесплатный деплой (GitHub Pages + Supabase)

Supabase уже настроен предыдущими разделами. Осталось выложить фронтенд.

### 1. Включите GitHub Pages

**Settings → Pages → Build and deployment → Source: GitHub Actions.**
(Один раз, дальше деплой запускается автоматически.)

### 2. Добавьте секреты и переменные репозитория

**Settings → Secrets and variables → Actions**:

Вкладка **Secrets** → New repository secret:
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Вкладка **Variables** → New repository variable:
- `VITE_VAPID_PUBLIC_KEY` (не секретный — публичный ключ и должен быть публичным)

### 3. Задеплойте

Запушьте в ветку `main` (workflow `.github/workflows/deploy.yml`
запустится автоматически) — либо, если `main` ещё не существует, откройте
вкладку **Actions → Deploy to GitHub Pages → Run workflow** и запустите
вручную.

Сайт появится по адресу вида `https://<ваш-логин>.github.io/g/`.

> Если репозиторий называется не `g`, откройте `vite.config.ts` и
> поменяйте `BASE_PATH` на `/имя-вашего-репозитория/` — иначе стили и
> иконки не подгрузятся на GitHub Pages (это единственное место в коде,
> которое явно завязано на имя репозитория).

## Переменные окружения

| Переменная | Обязательна | Где взять | Описание |
|---|---|---|---|
| `VITE_SUPABASE_URL` | Да | Supabase → Project Settings → Data API | Адрес вашего Supabase-проекта |
| `VITE_SUPABASE_ANON_KEY` | Да | Supabase → Project Settings → API Keys | Публичный ключ (безопасен для фронтенда — доступ ограничен через RLS) |
| `VITE_VAPID_PUBLIC_KEY` | Нет (без неё не будет push) | `npx web-push generate-vapid-keys` | Публичный VAPID-ключ для Web Push |

Серверные секреты Edge Function (не во фронтенде, а в Supabase):
`VAPID_PRIVATE_KEY`, `VAPID_PUBLIC_KEY`, `VAPID_SUBJECT` — см. раздел про
push. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Supabase подставляет
в Edge Function автоматически, ничего вводить не нужно.

## Установка PWA на телефон

### iPhone (Safari)

1. Откройте сайт в **Safari** (не в Chrome — на iOS это принципиально).
2. Нажмите кнопку **Поделиться** (квадрат со стрелкой вверх).
3. **На экран «Домой»** → **Добавить**.
4. Иконка появится на главном экране и открывается как отдельное
   приложение, без адресной строки браузера.

### Android (Chrome)

1. Откройте сайт в Chrome.
2. Либо появится баннер «Добавить на главный экран», либо откройте меню
   (три точки) → **Установить приложение** / **Добавить на главный экран**.

После установки на обеих платформах приложение открывается отдельной
иконкой, работает офлайн для уже открытых экранов (за счёт service
worker) и может присылать push-уведомления.

## Тесты

```bash
npm run typecheck   # проверка типов TypeScript
npm run lint         # ESLint
npm run test         # Vitest — вся бизнес-логика без БД
```

Автоматически покрыты тестами (`src/**/*.test.ts`):
- **`coverage.test.ts`** — расчёт покрытия «потребность vs факт»: точный
  пример из ТЗ (Иван 10–18, Мария 16–22:30 против потребности 14–18 на
  двоих → нехватка 1 человека с 14 до 16), отсутствие сотрудников,
  избыток, несколько требований в один день, пересекающиеся требования.
- **`shortageQueue.test.ts`** — приоритет посудомойщика над официантом,
  очерёдность внутри одной роли по времени создания.
- **`locales.test.ts`** — все три языковых файла содержат одинаковый
  набор ключей (не даёт забыть перевести что-то на один из языков).

```bash
deno test supabase/functions/send-push   # требует установленный Deno
```

Проверяет, что текст push-уведомлений формируется корректно на всех трёх
языках для каждого типа события, включая точный пример из ТЗ §10.

### SQL / права доступа / атомарность

Это самая важная и самая рискованная часть системы, поэтому она
проверена отдельно и особенно тщательно — не просто написана, а
**исполнена** против настоящего PostgreSQL с политиками Row Level
Security, максимально приближенными к реальному Supabase (включая
проверку через настоящий PostgREST по HTTP, чтобы поймать ошибки формата
данных, которые не видны при прямых SQL-запросах). Так в процессе
разработки были найдены и исправлены два реальных бага: неправильная
нормализация российских номеров телефона (8 vs +7) и утечка списка
сотрудников через view анонимным (ещё не вошедшим) посетителям.

Проверены вручную (напишите свои сценарии в SQL Editor или через API,
если хотите повторить — файлы миграций содержат все нужные функции):

- один/несколько сотрудников, частичное перекрытие смен, отсутствие и
  избыток сотрудников — покрыто `coverage.test.ts`;
- нехватка одного и нескольких сотрудников одновременно у официантов и
  посудомойщиков — обнаружение проверено против реальной БД;
- приоритет посудомойщика в очереди запросов — проверено и как чистая
  логика (`shortageQueue.test.ts`), и в БД (какой запрос открывается
  следующим);
- **два одновременных согласия на один слот** — проверено по-настоящему
  параллельно: 6 отдельных подключений к базе данных одновременно
  нажимают «Я выйду» на слот с needed_count=2 → ровно 2 успевают, ровно 2
  смены создаются, переполнения никогда не происходит (тест повторялся
  несколько раз подряд для исключения случайности);
- все отказались → администратор получает уведомление, запрос закрывается;
- админ пропустил дефицит → больше не создаёт уведомлений, даже если
  ситуация ухудшается;
- админ изменил смену → сотрудник получает уведомление со старым и новым
  временем;
- пришёл раньше/позже — фиксируется точное время без округления;
  сотрудник забыл отметить уход — админ может исправить время вручную,
  исправление попадает в историю;
- изменение расписания после первоначального заполнения — повторное
  сохранение того же дня обновляет ту же запись, а не создаёт вторую.

## Что легко расширить

Архитектура намеренно оставляет точки для будущего роста без переписывания:

- **Несколько недель.** `schedule_weeks` — уже таблица (не одна строка
  «зашитая» в код), просто пока используется одна строка с
  `is_active = true`. Чтобы добавить автоматическое создание следующей
  недели, нужна ОДНА новая функция (например, по расписанию `pg_cron`),
  копирующая `staffing_requirements` на новую неделю — остальной код
  (расчёт покрытия, смены, дефицит) уже параметризован по `week_id` и
  никаких изменений не потребует.
- **Другие роли**, кроме официанта/посудомойщика — добавляются одним
  значением в `enum public.staff_role`.
- **Напоминание о незаполненном расписании** (§25 ТЗ) — вся
  инфраструктура уведомлений и push уже есть; не хватает только
  `pg_cron`-задачи, которая раз в день ищет сотрудников без смен на
  активную неделю и вставляет строку в `notifications`.
- **Несколько ресторанов** — потребует добавить `restaurant_id` в
  ключевые таблицы; RLS-политики уже написаны как переиспользуемые
  функции (`is_admin()`, `current_employee_id()`), их легко расширить
  проверкой принадлежности ресторану.

## Известные ограничения версии 1

Честно о том, что не проверено или сознательно упрощено:

- Реальная **доставка** push-уведомлений (последний шаг: браузер →
  push-сервис → устройство) не была протестирована end-to-end в среде
  разработки этой сессии из-за сетевых ограничений песочницы — см. раздел
  про push. Логика формирования и отправки проверена полностью, кроме
  самого последнего сетевого прыжка.
- Согласно ТЗ §37, сознательно не реализованы: зарплата, табель, отпуска,
  больничные, чат, фотографии, несколько ресторанов, аналитика,
  автоматическое создание следующих недель.
- Главный бандл фронтенда — около 165 КБ в сжатом виде; для ~20 сотрудников и
  одной недели это не влияет на скорость, но при дальнейшем росте
  функциональности имеет смысл разбить его на части (`dynamic import`).
